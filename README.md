# 마중 (majung)

공항에 가족·지인을 마중 나가는 사람이, 항공편 도착 정보와 이동 시간을 바탕으로 **추천 출발 시각**을 확인하고, 도착 정보가 바뀌면 다시 안내받는 모바일 웹 서비스입니다.

> ⚠️ **항공편 · 장소 검색 · 이동 시간(길찾기)이 모두 서버 함수로 실제 API에 연결되어 있고, 로컬 임시 서버에서 실제 호출로 브라우저 확인까지 했습니다(2026-10-31, "검증 현황" 1번 표). 다만 아직 배포하지 않았습니다. Netlify 배포와 배포 후 동작은 확인하지 못했습니다.** 경로 없음 화면 · 터미널을 모르는 편의 화면 · 도착 시각이 바뀌었을 때 변경 안내 띠의 "이동 시간도 다시 확인했어요" 문구 · 화면 읽기 프로그램 · 오류 경로의 서버 로그 · 카카오 쪽 보관과 이용약관 해석 · 목적지 좌표가 마중객이 실제로 가는 곳과 같은지는 아직 확인하지 않았습니다(아래 "알려진 제약", "아직 확인 못 한 것"). 주소 끝에 `?scenario=이름`을 붙이면 항공편 · 장소 · 이동 시간이 모두 목업인 "시나리오 모드"입니다. (아래 "모드" 참고)

- 요구사항: [CLAUDE.md](CLAUDE.md) · 디자인 규칙: [DesignGuide.md](DesignGuide.md)
- 스택: 순수 HTML / CSS / JavaScript (ES 모듈). 빌드 도구와 외부 패키지 없음.

## 실행 방법

```bash
npm start        # http://localhost:5173 (Python 3.7 이상의 http.server로 public/ 폴더를 제공)
npm test         # 계산·변경 감지·상태 판단 단위 테스트 (Node 20 이상, node:test)
```

- ES 모듈을 쓰기 때문에 `public/index.html`을 더블클릭(`file://`)해서는 동작하지 않습니다. 로컬 서버로 열어야 합니다.
- Python이 없다면 아무 정적 파일 서버(예: VS Code Live Server)로 `public/` 폴더를 서버의 루트로 열면 됩니다.
- 글꼴(Pretendard)은 CDN에서 받아 오므로 인터넷 연결이 필요합니다. 연결이 없으면 시스템 글꼴로 보입니다.

## 화면 흐름

| 단계 | 화면 | 주소 해시 |
|---|---|---|
| 1 | 항공편 찾기 (편명 + 도착 날짜) | `#/flight` |
| 2 | 항공편 확인 (카드에서 직접 선택) | `#/confirm` |
| 3 | 출발지 설정 (주소 검색 → 선택 → 이동 시간 조회) | `#/origin` |
| 4 | 추천 출발 시각 (카드 · 근거 칩 · 여유 시간 수정 · 변경 안내) | `#/result` |

앞 단계를 거치지 않고 뒤 단계 주소로 들어오면 갈 수 있는 가장 가까운 앞 단계로 이동합니다.

## 모드: 실제 모드와 시나리오 모드

| 모드 | 조건 | 항공편 | 주소·이동 시간 | 시계 | 상단 표시 |
|---|---|---|---|---|---|
| 실제 모드 | 주소에 `?scenario=`가 없음 (알 수 없는 이름도 여기) | 서버 함수 `/api/flights`로 인천공항 API 조회 | 장소 검색: 서버 함수 `/api/places`로 카카오 로컬 API 조회 · 이동 시간: 서버 함수 `/api/route`로 카카오모빌리티 길찾기 조회(도착 터미널 P01·P03만) | **실제 시각** | 표시 없음 (`ADDRESS_ROUTE_IS_MOCK`가 `false`) |
| 시나리오 모드 | `?scenario=이름` (아래 표의 이름) | 목업 | 목업 | **데모 시계** | "목업 데이터" (이름이 `normal`이 아니면 "목업 · 이름") |

- 모드와 시계는 `public/js/clock.js` 한 곳에서 고릅니다. `ctx.now`·`ctx.today`와 목업 어댑터의 `fetchedAt`이 모두 여기를 거칩니다. "오늘" 날짜는 두 모드 모두 실제 한국 날짜이고, 데모 시계는 시각(시·분)만 바꿉니다.
- 실제 모드에서 항공편의 `fetchedAt`은 **서버가 인천공항 API를 부르기 직전의 시각**이고 "N:NN에 확인했어요" **표시에만** 씁니다. "오래됨" 판단과 자동 재확인은 화면이 응답을 받은 시각(`receivedAt`, 기기 시계)에서 잰 **경과 시간**으로 하므로 서버 시계와 기기 시계의 차이에 영향받지 않습니다. 단점은 아래 "갱신"에 적었습니다.
- 주소·이동 시간이 모두 실제로 연결되고 사용자가 브라우저에서 확인해(2026-10-31) `config.js`의 `ADDRESS_ROUTE_IS_MOCK`을 `false`로 바꿨습니다. 이 값은 **상단 표시에만** 쓰이고(코드 검색과 테스트로 확인), `false`면 실제 모드의 상단 표시가 없습니다. 시나리오 모드는 이 값과 상관없이 "목업 데이터"(이름이 `normal`이 아니면 "목업 · 이름")입니다. 문구 결정은 `domain/mockBadge.js`이고 테스트(`tests/mockBadge.test.js`)로 고정했습니다. 상단 표시를 없앤 뒤 실제 모드 첫 화면을 브라우저에서 본 확인은 **아직 없습니다.** 다시 목업이 섞이게 되면 `true`로 되돌리면 "주소·이동 시간은 예시"가 나옵니다.
- (임시 결정) 이동 시간이 목업인 실제 모드에서는 "이동 시간도 다시 확인했어요"와 이동 시간 비교 줄을 쓰지 않습니다. 목업 이동 시간은 다시 조회해도 같은 값이라 사실이 아니기 때문입니다. 시나리오 모드(전부 목업, 상단에 표시됨)에서는 변경 안내를 보여 주려고 그대로 씁니다.

### 시나리오

주소 끝에 `?scenario=이름`을 붙입니다. 예: `http://localhost:5173/?scenario=changed`
**시나리오를 바꾼 뒤에는 첫 화면부터 다시 조회하세요.** (이전 시나리오의 저장값이 남아 있으면 섞여 보입니다.)
화면 오른쪽 위 "목업 데이터" 표시에 현재 시나리오 이름이 함께 보입니다.

| 이름 | 보여 주는 상황 |
|---|---|
| `normal` (기본) | 정상. 추천 출발 시각과 "여유 있어요" |
| `changed` | 화면을 열면 도착 시각이 바뀌어 있고, 이동 시간도 다시 조회되어 변경 안내 띠가 나타남 |
| `stale` | 처음 조회는 되지만 이후 확인이 실패해 "최신 정보를 확인하지 못했어요" + 마지막 확인 시각 |
| `fail` | 항공편 조회 실패 (일시적 오류) → "다시 시도" |
| `notfound` | 해당 날짜에 항공편 없음 |
| `routefail` | 이동 시간 조회 실패 (출발지 단계에서 막힘) |
| `passed` | 추천 출발 시각이 이미 지남 → "이동 시간 다시 확인" |
| `recheckfail` | 출발 시각이 지난 상태에서 "이동 시간 다시 확인"만 실패 |
| `landed` | 이미 도착한 항공편 (status `arrived`) → 추천 카드 대신 안내 상자 |
| `touchdown` | 착륙한 항공편 → 추천 카드는 유지하고 말풍선만 바뀜 |
| `unknown` | 알 수 없는 운항 상태(결항·회항 포함) → 추천 시각을 계산하지 않고 안내 상자 |
| `later-touchdown` · `later-arrived` · `later-unknown` | 화면을 열어 둔 사이 상태가 바뀜(착륙 / 도착 / 알 수 없는 상태). 검색과 첫 재확인은 상태 없음이고 **두 번째 재확인부터** 바뀜. 보려면 추천 시각 화면을 연 채 **약 1분** 기다림 (데모 시계가 11배 빨라 1분 뒤 점검에서 자동 재확인이 일어남) |

목업 항공편: `KE123`(오늘·내일, 17:30), `OZ541`(오늘 23:50, 변경 시 다음 날 00:20), `LJ202`(오늘 19:05, 구분 정보 없음).
목업 출발지: 합정역·강남역·서울역·판교역·송도 센트럴파크.

시나리오 모드는 **데모 시계**를 씁니다. (실제 모드는 실제 시각입니다.) 기본은 오늘 14:00에서 시작해 페이지를 연 뒤 지난 시간만큼 흐르고, `passed`·`recheckfail`은 16:00에서 시작합니다. (실제 시각을 쓰면 밤에 열 때마다 "출발 시각 지남"이 나오기 때문입니다.)

```
  index.html            단일 페이지 (양옆 모션 배경 SVG 포함)
  css/                  tokens(디자인 값) · base · layout · components

    config.js           ★ 설정 상수의 단일 출처 (아래 참고)

    adapters/           항공편 · 주소(둘 다 실제 모드는 서버 함수 호출, 시나리오 모드는 목업) · 이동 시간(목업, 실제 API로 교체할 경계)
    mock/               목업 데이터와 시나리오 스위치 · 데모 시계
    ui/screens/         화면 4개
    ui/components/      카드 · 칩 · 배지 · 변경 띠 · 바텀시트 · 진행 바 · 아이콘
  assets/icons/         1.5px 선형 SVG 아이콘 + 로고
server/
  icn/                  인천공항 API 응답 변환: 시각(kst) · 오류 분류 · 도착편 변환(순수 함수, 네트워크·키 없음)
                        + handleFlights.js (키·fetch·시계를 받아 호출·캐시 헤더·오류 응답을 만드는 함수 본체)
tests/                  단위 테스트 (public/js 와 server/ 의 순수 함수를 불러와 검사)
  helpers/              테스트 공용 도구: 네트워크(fetch) 차단, fixture 읽기
```

## 설정 상수 (`public/js/config.js`)

숫자를 바꾸려면 이 파일만 고치면 화면·계산·테스트에 모두 반영됩니다.

| 상수 | 값 | 뜻 |
|---|---|---|
| `DEFAULT_AIRPORT_BUFFER_MIN` / `DEFAULT_MEETUP_MIN` | 20 / 40 | 공항 도착 여유 / 입국 후 만남까지 기본값(분). 사용자가 바텀시트에서 바꾸는 "설정값" |
| `BUFFER_STEP_MIN`, `BUFFER_MIN_MIN`, `BUFFER_MAX_MIN` | 5, 0, 120 | 바텀시트 −/+ 단위와 범위 (가정) |
| `SOON_THRESHOLD_MIN` | 60 | 추천 출발 60분 전부터 "곧 나갈 시간이에요" (가정) |
| `STALE_AFTER_MIN` | 10 | 화면이 응답을 받은 지 10분이 지나면 "최신 정보를 확인하지 못했어요". 화면을 연 채 이 시간이 지나면 자동으로 한 번 다시 확인하는 간격으로도 사용 (가정, API 호출 한도 확인 후 조정) |
| `BADGE_PRIORITY` | 지남 > 오래됨 > 변경 > 곧 출발 > 여유 | 상태 배지가 겹칠 때 먼저 보일 순서 |
| `STATUS_RECHECK_INTERVAL_MS` | 60000 | 화면을 열어 둔 동안 배지를 다시 판단하는 간격 (이 판단은 API 호출이 아님. 자동 재확인은 이 간격으로 감지되어 `STALE_AFTER_MIN`보다 최대 이 간격만큼 늦게 일어남) |
| `ADDRESS_SEARCH_DEBOUNCE_MS`, `ADDRESS_MIN_QUERY_LENGTH` | 400, 2 | 주소 검색 호출을 아끼기 위한 값 (가정) |

## 추천 시각 계산

```
추천 출발 시각 = 예상 도착 시각 − 이동 시간 − 공항 도착 여유 − 입국 후 만남까지 예상 시간
```

- 예상 도착 시각은 변경 도착 시각이 있으면 그것을, 없으면 예정 도착 시각을 씁니다.
- 도착이 늦어졌다고 출발을 같은 분량만큼 미루지 않고, 변경 시점에 이동 시간을 다시 조회해 다시 계산합니다.
- 공항 도착 여유와 입국 후 만남까지 시간은 **사용자가 정하는 설정값**이며, 실제 입국 처리 시간이 아닙니다.
- 추천 시각은 보장이 아니라 **예상**이라는 안내를 카드에서 항상 보여 줍니다.

## 환경변수

`.env.example`에 변수 이름과 설명만 있습니다. 키는 서버 환경변수로만 읽고, 소스·Git·브라우저 번들·로그에 넣지 않습니다. `.env`는 `.gitignore`에 포함되어 있습니다.

| 변수 | 지금 쓰는가 | 뜻 |
|---|---|---|
| `ICN_AIRPORT_API_KEY` | **쓴다** (`netlify/functions/flights.mjs`) | 공공데이터포털 서비스 키. 이미 인코딩된 키(`%`가 든 키)를 넣어도 한 번 풀어서 쓴다 |
| `KAKAO_REST_API_KEY` | **쓴다** (`netlify/functions/places.mjs`, `route.mjs`) | 카카오 로컬(장소 검색)·카카오모빌리티 길찾기 REST API 키. 서버 함수만 읽는다 |
| `KAKAO_JAVASCRIPT_KEY` | 안 쓴다 | 지도(P1) |

- Netlify: 범위(Scopes) 선택은 Pro 이상, 그 외에는 기본으로 전체 적용. 실제 화면에서 보이는지는 배포 때 확인. 바꾼 뒤에는 **다시 배포**해야 반영됩니다. (docs.netlify.com "Environment variables" 기준. 이 프로젝트에서 실제로 확인한 것은 아님)
- 로컬에서 함수까지 확인하려면 저장소 밖의 임시 서버 스크립트를 쓸 수 있습니다. 이 방법은 **실행해 본 적이 없습니다**(스크립트가 뜨고 정적 파일·잘못된 요청 응답까지만 확인함). `netlify dev`는 설치가 필요해 쓰지 않았습니다.

## 알려진 제약

- **연결 상태:** 인천국제공항공사 여객기 운항 현황 상세 조회 서비스는 서버 함수(`/api/flights`)와 화면 어댑터까지 **코드로 연결**했지만, 이 함수를 배포하거나 브라우저에서 실제로 호출해 본 적은 **없습니다**(테스트는 가짜 `fetch`로만 돌렸습니다). 카카오 로컬 API(장소 검색)는 서버 함수(`/api/places`)와 화면 어댑터까지 **코드로 연결**했고, 배포는 **하지 않았습니다**. 로컬 임시 서버에서의 실제 카카오 호출은 사용자가 브라우저로 확인했습니다("검증 현황" 1번 표). 카카오모빌리티 길찾기 API(이동 시간)는 서버 함수(`/api/route`)와 화면 어댑터까지 **코드로 연결**했지만, 브라우저에서 실제로 호출해 확인한 것은 **아직 없습니다**(테스트는 가짜 `fetch`로만). 시나리오 모드의 이동 시간은 목업입니다. 응답 필드·호출 한도는 공식 명세와 샘플 조회로 확인한 범위까지만 믿습니다.
- **아직 배포하지 않았습니다:** 이동 시간 값은 실제가 되었고 사용자가 로컬 임시 서버(실제 모드)에서 실제 카카오 호출로 브라우저 확인을 했습니다(2026-10-31, "검증 현황" 1번 표). 그러나 Netlify 배포와 배포 후 동작은 하지도 확인하지도 못했습니다. 샘플 호출(2026-10-31)로 확인한 것은 응답 모양(성공: HTTP 200 · `result_code` 0, 경로 없음: HTTP 200 · `result_code` 102 · 104, 잘못된 입력: HTTP 400 · `{ code, msg }`)까지이고, 키 권한 · 한도 초과 응답은 **확인 못 했습니다.** 경로 없음은 화면에서 확인하지 못했고(샘플 호출과 테스트로만), 목적지 좌표(도착층)가 마중객이 실제로 가는 곳과 같은지도 확인 못 했습니다.
- **고정 예시 이동 시간은 시나리오 모드에서만 씁니다:** `EXAMPLE_DRIVE`(60분 · 55km, `source: 'mock'`)는 시나리오 모드에서 목업에 없는 장소 id를 위해서만 남았습니다. 실제 모드는 길찾기가 실패해도 이 값이나 `MOCK_DRIVE`를 돌려주지 않아 가짜 값이 실제 값처럼 보이지 않습니다(테스트로 확인).
- **이동 시간(길찾기) 연결:** 실제 모드에서 출발지 좌표(경도·위도)와 항공편의 도착 터미널 코드(`P01` · `P03`)를 브라우저 → 서버 함수(`/api/route`, POST 본문) → 카카오모빌리티 길찾기로 전달합니다. 목적지 좌표는 클라이언트가 보내지 않고 서버 안 표(`server/kakao/destinations.js`)에서 고릅니다. 결과의 `source`는 `'kakao'`입니다.
  - **터미널을 모르는 편(없거나 P02):** 서버를 부르지 않고 추천 카드 대신 "이 항공편의 도착 터미널을 확인하지 못해서 이동 시간을 계산하지 못했어요." 안내 상자를 보여 줍니다(문구는 DesignGuide 초안, 가정). 출발지 화면은 이 경우에도 다음 화면으로 넘어가며 이동 시간 자리에 빈 값(`minutes: null`)을 저장하는데, 이 값은 이동 시간으로 쓰이지 않습니다. 시나리오 모드에는 적용하지 않습니다(목업 항공편에 터미널이 없음).
  - **경로 없음:** `noroute`(HTTP 200 + `ok: false`)는 출발지 화면에서 "다른 출발지를 골라 주실래요?" 취지의 안내(초안)를 보여 주고 "다시 시도"는 없습니다. 한도 초과 · 시간 초과 · 서버 오류 등 그 밖의 실패는 기존 "이동 시간을 불러오지 못해서…" 안내와 "다시 시도"입니다. 도착 변경이나 "이동 시간 다시 확인"의 재조회가 실패하면 이전 값을 그대로 둡니다.
  - **"이동 시간도 다시 확인했어요":** `source`가 `'kakao'`이면 실제 모드에서도 도착 시각이 바뀌어 재조회에 성공했을 때 씁니다(`isRealTravelRecheck`, 테스트로 확인). 이동 시간이 달라졌을 때만 비교 줄이 나옵니다. 이 문구는 도착 시각이 바뀌어 재조회에 성공했을 때의 변경 안내 띠에서만 나옵니다. **브라우저에서 이 문구가 화면에 나타나는 것은 아직 확인하지 않았습니다**(코드와 테스트로만 확인). 이동 시간 값이 같을 때 나오지 않는지도 확인하지 않았습니다.
  - **이동 시간 확인 줄:** 추천 카드의 근거 칩 아래에 "이동 시간은 18:45에 확인했어요" 줄을 추가했습니다(문구는 DesignGuide §6 초안, 가정). `store.drive.fetchedAt`(`routeAdapter`가 기기 시계로 저장한 이동 시간 조회 시각)을 읽어 표시만 하고 API 호출은 늘리지 않았습니다. 실제 모드에서 `source`가 `'kakao'`일 때만 보이고, 시나리오 모드의 목업 값 · 확인 시각이 없는 이전 저장값 · 이동 시간이 없는 터미널 보류 상태에서는 숨깁니다. "이동 시간 다시 확인"이 성공하면(`drive`를 바꾼 뒤 카드를 다시 그리는 코드를 읽어 확인) 새 시각으로 바뀌고, 실패해 이전 값을 두면 그대로입니다. "교통을 반영했다"는 뜻의 문구는 쓰지 않았습니다(카카오가 실시간 교통을 반영하는지 확인 못 함). 사용자가 2026-10-31에 브라우저(실제 모드)에서 이 줄이 표시되는 것, "이동 시간 다시 확인" 뒤 이 줄의 시각이 바뀌는 것, 시나리오 모드에서는 이 줄이 보이지 않는 것을 확인했습니다.
    - 항공편 확인 시각 줄, "마지막 확인은 N:NN예요", "오래됨" 판단, 자동 재확인은 항공편 기준 그대로입니다. 두 시각은 시계가 달라(서버 / 기기) 서로 비교하지 않습니다. **이동 시간에는 "오래됨" 기준을 두지 않았습니다**(둘 때 필요한 것은 아래 "나중에 할 일").
    - 단위 테스트는 문구 · 숨김 조건 · 시각 형식 · 뷰모델 · 카드 안 위치까지입니다(`tests/travelChecked.test.js`). 좁은 폭에서 줄바꿈이 어색하지 않았다는 것은 사용자가 2026-10-31에 확인했지만 어느 폭인지는 기록이 없고, 화면 읽기 프로그램은 **확인 전**입니다. 시각은 시·분만 보여 주고 날짜는 보여 주지 않습니다.
  - **제한:** 터미널을 몰라 보류된 편은 자동으로 다시 확인하지 않습니다(터미널이 나중에 정해져도 "항공편 바꾸기"로 다시 와야 합니다). 항공편을 바꾼 뒤 결과 화면 주소로 바로 들어가면 이전 항공편(다른 터미널)의 이동 시간이 남아 있을 수 있고, 출발지 화면을 거치면 새로 계산됩니다.
- **장소 검색어·출발지 좌표의 흐름과 확인 범위:** 실제 모드에서 입력한 검색어(2글자 이상, 앞뒤 공백 제외)는 브라우저 → 서버 함수(`/api/places`, POST 본문) → 카카오 로컬 API로, 고른 출발지의 좌표(경도·위도)와 도착 터미널 코드는 브라우저 → 서버 함수(`/api/route`, POST 본문) → 카카오모빌리티 길찾기로 전달됩니다. 시나리오 모드(`?scenario=`)는 서버를 부르지 않습니다.
  - **코드를 읽고 확인한 것 (가정: 코드 기준, 실제 동작은 확인 못 함):** 서버 함수는 검색어를 저장하지 않고(파일·DB·메모리 보관 코드 없음), 응답에 `Cache-Control: no-store`를 붙이고, 로그에는 reason·상태 코드·받은 건수만 남깁니다(검색어·주소·키 없음, 테스트로 확인). 브라우저 콘솔에도 검색어를 남기지 않습니다. 검색어는 주소(URL)가 아니라 본문으로 보냅니다. 키는 서버 환경변수 `KAKAO_REST_API_KEY`에서만 읽고 브라우저에는 없습니다. 브라우저는 검색어를 저장하지 않으며, **사용자가 고른 장소 한 곳**(이름·주소·좌표)과 조회한 이동 시간·거리만 `sessionStorage`에 둡니다(탭을 닫으면 지워짐). 길찾기 서버 함수도 같은 방식입니다: 좌표를 저장하는 코드가 없고, 응답에 `Cache-Control: no-store`를 붙이고, 로그에는 reason·상태 코드·분만 남깁니다(좌표·터미널 코드·키 없음, 테스트로 확인). 브라우저 콘솔에도 좌표·장소 이름을 남기지 않습니다(테스트로 확인).
  - **확인 못 한 것:** (1) Netlify 쪽 보관: 함수 실행 로그·요청 로그·플랫폼 기능이 POST 본문이나 검색어를 남기는지. (2) 카카오 쪽 보관: 카카오가 검색어와 요청 정보를 얼마나 보관하는지. (3) 이용약관의 저장·캐시 제한: 카카오 로컬 API 결과와 길찾기 결과(이동 시간·거리)를 `sessionStorage`에 두는 것이 허용되는지 약관을 해석해 확인하지 못했습니다. 카카오 개발자 서비스 약관(제5조, 시행일 2026-04-20, 문서 확인 2026-10-31)에 앱 사용자 환경 개선 목적 외의 캐시를 금지하는 조항이 있다는 것까지만 확인했습니다. (4) 위치정보(좌표) 관련 약관 조항: 확인한 문서에서 찾지 못했고, 있는지 여부도 **확인 못 함**입니다. (5) 목적지 좌표(카카오 장소 검색 결과의 좌표)를 코드의 표에 직접 적어 두는 것이 약관상 허용되는지의 해석도 **확인 못 함**입니다. 그래서 화면의 "마중은 이 장소를 저장하지 않고"는 우리 서버와 앱이 저장하지 않는다는 뜻으로만 읽어야 하며, 카카오가 저장하지 않는다는 뜻이 아닙니다(가정).
- **실제 모드의 브라우저 확인 범위:** 저장소 밖 로컬 임시 서버(`dev-server.mjs`)에 `/api/places` 연결을 추가한 뒤 사용자가 2026-10-31에 실제 카카오 호출로 확인한 범위(장소 검색)는 "검증 현황" 1번 표에, 확인하지 않은 것은 4번 표의 "장소 검색 (실제 모드)"·"이동 시간 (실제 모드)" 행에 있습니다. 이동 시간(`/api/route`)도 개발 서버에 연결을 추가해 사용자가 2026-10-31에 같은 방식으로 확인했습니다(1번 표).
- **장소 검색의 실패 문구:** 서버 reason(`invalid` · `config` · `quota` · `error`)과 시간 초과는 모두 같은 "지금은 주소를 검색하지 못했어요" 문구로 보여 줍니다. 한도 초과 전용 문구는 DesignGuide에 없어 만들지 않았습니다. 결과 없음은 오류가 아니라 "이 주소를 찾지 못했어요" 안내입니다.
- **같은 장소의 여러 줄:** 같은 역이 노선별로 두 줄 이상 와도 합치지 않고 받은 그대로 보여 줍니다. 한 번에 최대 15건(1쪽)이고 다음 쪽은 부르지 않습니다.
- **항공편 정보 범위:** 출발 도시는 API의 `airport`(출발지 공항 한글명)를 그대로 보여 줍니다. 도시 이름이 아닐 수 있습니다. 도착 정보 변경 감지는 도착 시각만 비교하며, 운항 상태는 비교하지 않습니다. 터미널·일찍/늦게 안내 줄은 아직 화면에 연결하지 않았습니다.
- **`landed` 판단 (임시 결정):** 화면 어댑터가 `status`가 `arrived`(도착)일 때만 `landed`를 true로 하고, `touchdown`(착륙)은 false로 둡니다. 도착은 추천 카드 대신 안내 상자, 착륙은 추천 카드를 유지하고 말풍선만 바뀝니다. 착륙 편의 변경 시각은 실제 시각이 아닐 수 있다는 관찰이 있어서, 근거 칩의 "비행기 도착" 시각은 계산에 쓴 값이라 그대로 보여 주되 DesignGuide에 그 사실을 적어 두었습니다. 결항·회항은 아직 관찰하지 못했고, 알아보지 못한 상태(`unknown`)는 추천 시각을 계산하지 않고 안내 상자를 보여 줍니다. 이 규칙은 실제 값을 더 확인한 뒤 바뀔 수 있습니다.
- **호출 한도 대책 (서버 함수):** 항공편 조회는 GET이고, 성공 응답에만 Netlify CDN 캐시 5분(가정, `Netlify-CDN-Cache-Control: public, s-maxage=300`)을 붙입니다. 브라우저는 매번 다시 확인하게(`Cache-Control: public, max-age=0, must-revalidate`) 두고, 오류·0건 응답은 `no-store`입니다. 응답 안의 `fetchedAt`은 서버가 인천공항 API를 부른 시각 그대로라 캐시에서 나가도 "마지막 확인 시각"이 거짓이 되지 않습니다. 헤더 이름은 docs.netlify.com "Caching overview"로 확인했고, 실제 캐시가 동작하는지는 배포 후에만 확인할 수 있습니다. 공공데이터포털은 https로만 부르고 실패해도 http로 바꾸지 않습니다. 한 요청에 외부 호출은 최대 1번입니다.
- **재확인의 조회 날짜:** 이미 고른 항공편을 다시 확인할 때는 `f_id`와 그 편의 `arrivalDate`(예정 도착 날짜)를 `searchday`로 보냅니다. `f_id`만 보내면 오늘 날짜로 조회되는 것이 샘플로 관찰됐고, 다른 날짜의 `searchday`로 부르면 0건이 왔습니다. 자정을 넘겨 변경 도착 날짜가 바뀌는 편에서 이 날짜 기준이 맞는지는 **확인 못 함**입니다.
- **아직 만들지 않은 DesignGuide 항목:** 변경 안내 띠의 "직전 조회 대비 5분 · 처음 조회와 착륙·도착 이후에는 띠 없음" 기준, "예정 차이 줄", "이번 조회에서 안 보임" 안내(재확인이 0건일 때 `missing`을 돌려주지만 화면은 이전 값을 유지할 뿐 안내 줄을 보여 주지 않음), 호출 한도 초과 시 재확인 안내.
- **지연 기준·변경 시각의 의미(실제 API를 연결할 때 적용할 내용):** 항공편 조회 API의 활용가이드에는 `remark`의 "지연"이 몇 분부터인지, 그리고 착륙·도착 뒤에 변경 시각(`estimatedDateTime`)이 실제 시각으로 바뀌는지에 대한 기준이 **없습니다.** 2026-10-30 오전 11시 47분에 오늘 도착편 1,153건 전체를 관찰한 결과는 다음과 같으며, 문서 근거가 아니라 **관찰**입니다. (다른 날짜·시간대에서는 달라질 수 있습니다.)
  - `remark` 값은 도착 401건, 착륙 2건, 지연 45건, 값 없음(null) 705건이었습니다. 결항·회항은 그날 나오지 않았지만 없다고 단정하지 않습니다.
  - "지연" 45건은 모두 변경 시각이 예정보다 16~91분 늦은 편이었고, `remark`가 비어 있으면서 정확히 15분 늦은 편이 4건 있었습니다. 즉 착륙 전에는 16분 이상 늦은 편이 "지연"으로 표시된 것으로 보입니다.
  - "도착"으로 표시된 편 401건 중 394건은 변경 시각이 예정과 달라(최대 43분 빠름 ~ 82분 늦음), 이 경우 변경 시각은 이미 지난 시각이라 실제 도착 시각으로 보입니다(샘플 호출에서 "도착" 19건의 변경 시각이 모두 호출 시각보다 앞이었습니다). 반면 **"착륙"의 변경 시각은 실제 시각이 아닙니다.** 같은 샘플에서 "착륙" 5건 중 4건(서로 다른 편으로는 3편 중 2편)의 변경 시각이 호출 시각보다 약 4분 **뒤**였습니다. "도착"이 되면 "지연" 라벨이 사라집니다(도착 401건 중 15분 이상 늦은 121건이 모두 `remark`가 "도착"이었습니다). 그래서 `remark`만으로는 늦게 도착했는지 알 수 없습니다. "착륙"일 때 라벨이 어떻게 되는지는 표본이 2행뿐이라 **확인 못 함**입니다.
  - 그래서 어댑터는 예정과 변경 시각의 차이를 **분 단위 숫자**(늦으면 +, 빠르면 −)로 함께 돌려주고, 변경 시각의 성격(착륙 전 예상 / 착륙 / 도착 기록 / 알 수 없음)도 구분해서 돌려줍니다. **몇 분 이상을 안내할지는 어댑터가 아니라 화면 쪽 설정**(`EARLY_NOTICE_MIN`, `LATE_NOTICE_MIN`)으로 둡니다. 어댑터에는 임의의 지연 기준을 넣지 않습니다.
  - **안내 기준 (제품 판단, 가정. 문서 근거 없음):** 예정보다 **10분 이상 일찍**(차이 −10분 이하) 또는 **15분 이상 늦게**(+15분 이상) 도착하는, **착륙 전** 편만 안내 대상으로 봅니다. 일찍 오는 편을 놓치면 승객이 기다리게 되므로 일찍 쪽을 더 민감하게 잡았고, 늦게 쪽은 공항의 "지연" 표시가 16분 이상으로 관찰된 것과 비슷하게 맞췄습니다. 이 기준은 **안내를 띄울지**에만 쓰고, 추천 출발 시각 계산에는 쓰지 않습니다(항상 최신 변경 시각을 씁니다). 도착까지 남은 시간에 따라 기준을 바꾸지 않습니다. 시간대별 비율이 일정하게 늘지 않고 표본이 작아 근거가 부족합니다. 강조(색·아이콘·알림)를 붙이는 기준과 숫자만 보여 주는 기준을 나눌지는 DesignGuide 문구를 정할 때 결정합니다.

    - 변경 시각이 예정과 다른 편 369건(49%): 일찍 221건, 늦게 148건.
    - 10분 이상 일찍 132건, 15분 이상 늦게 49건 → 두 기준으로 안내 대상 181건(24%).
    - 도착까지 2시간 이내 편 103건 중 41건(약 40%)이 10분 이상 달라져 있었습니다. 이 103건에는 **예정 시각이 이미 지났는데 아직 도착하지 않은 4건이 포함**되어 있고, 이를 뺀 정확히 2시간 이내로는 99건 중 37건(37%)입니다.
    - 시간대별 비율은 도착까지 0~1시간 53%, 1~2시간 23%, 2~4시간 29%, 4~8시간 35%, 8시간 이상 10%였습니다.
- **응답이 여러 페이지여도 첫 페이지만 변환하고, 잘렸다는 표시만 남깁니다 (서버 함수가 `numOfRows` 500으로 한 번만 호출):** 검색 성공 결과에는 `truncated`(`totalCount`가 받은 행 수(유효한 행 + 버린 행)보다 크면 true)를 붙이지만, **다음 페이지는 자동으로 부르지 않습니다**(페이지마다 API 호출이 하루 한도에서 빠집니다). 재확인(`refresh`)과 오류 결과에는 붙이지 않습니다. 편명과 날짜(또는 `f_id`)로 조회하면 1건 안팎이라고 봅니다(KE5854와 CZ313은 각각 1건이었습니다). 같은 편명이 한 번에 10건을 넘길 수 있는지는 **확인 못 함**입니다. 화면에는 "결과가 더 있어요" 안내를 만들지 않기로 했고(DesignGuide 12장), 잘림 표시는 어댑터 반환값의 `meta.truncated`에만 남깁니다. 화면 어댑터는 요청한 날짜와 다른 행도 거르지 않고 `arrivalDate`와 함께 넘깁니다.

### 2. 자동 브라우저 점검으로 통과한 것

- **환경:** Chrome 156.0.8078.48 (Windows 11, headless), 로컬 서버(localhost), 임시 프로필, 폭 375 · 767 · 768 · 1280px
- **결과 (전부 현재 코드 기준):** 통과 116 · 실패 0 · 확인 못 함 4 (확인 못 한 4건은 아래 "아직 확인 못 한 것"에 있습니다)
  - 116 = 화면 동작 점검 104 + 시간이 흐른 경우(L10) 6 + 줄바꿈 · 가로 넘침 점검 6. 줄바꿈 규칙(`word-break: keep-all`)을 넣은 뒤의 코드에서 모두 다시 돌렸습니다.
  - 별도로 "비교 항목" 1건(`overflow-wrap: break-word`만 쓸 때와의 비교)이 있습니다. 앱의 통과·실패를 가리는 항목이 아니라서 위 개수에는 넣지 않았습니다.
- **이 점검의 스크린샷을 사용자가 본 것:** 자동 점검이 남긴 스크린샷을 사용자가 확인했습니다. (어떤 화면을 봤는지는 기록이 없습니다. 위 1번의 "내 브라우저에서 직접 본 것"과는 별개입니다. 스크린샷은 저장소에 포함하지 않았습니다.)
- **확인한 것:**
  - 첫 화면: 편명 정규화, 형식 오류 · 항공편 없음 · 조회 실패 문구 구분, "다시 시도", 날짜(오늘/내일)
  - 항공편 확인: 선택(Amber 배경 + 체크 아이콘), 같은 편명의 날짜 구분, 구분 정보가 없을 때 해당 줄 숨김
  - 출발지: 안내 문구, 주소 검색(2글자 미만 · 결과 · 없음), 이동 시간 조회 실패 시 다음 화면으로 넘어가지 않음
  - 추천 카드: 구성, 근거 칩 3개, "여유" 칩의 읽기용 문구(`aria-label`), 확인 시각과 "달라질 수 있어요" 안내
  - 바텀시트: 열기, 5분 단위, 0 · 120분 경계, Esc · 바깥 누르기로 닫기(저장 안 됨), Tab 가두기, 저장, 포커스 복귀, 새로고침 후 유지, **시트가 열린 채 자동 확인이 끝나 카드가 다시 그려져도 포커스가 새 "여유" 칩으로 돌아옴**
  - 변경 안내: 이전 → 새 값 · 취소선, 같은 변경은 한 번만 안내, 항공편을 새로 고르면 다시 안내, 자정을 넘기는 변경
  - 상태: 오래됨(추천 시각과 마지막 확인 시각 유지), 출발 시각 지남, 이동 시간 다시 확인 실패, 이미 도착
  - 화면을 연 채 시간이 지난 경우: 마지막 확인으로부터 10분이 지나면 자동으로 한 번 다시 확인, 실패하면 반복하지 않고 "다시 시도"로 넘김, 성공하면 다시 10분 뒤 한 번 더 확인
  - **화면을 열 때의 확인이 실패해도 자동으로 반복하지 않음** (열 때의 확인이 자동 시도 1회로 셈됨)
  - 글자 버튼 정렬(카드 왼쪽 가장자리 · 안내 상자 안쪽 여백), 터치 영역 48px 유지
  - 양옆 모션 배경: 767px에서는 숨김, 768px부터 보임, 실제 움직임 폭, "움직임 줄이기"에서 멈춤
  - 레이아웃: 가로 스크롤 없음, 보이는 글자 14px 이상, 확대(핀치 줌)를 막지 않는 설정
  - 콘솔 오류 · 자바스크립트 예외 · localhost 요청 실패(404 등) 0건
  - **줄바꿈과 가로 넘침** (`word-break: keep-all`, `overflow-wrap: anywhere`를 넣은 뒤). "고치기 전" 값은 규칙이 없던 **이전 커밋을 임시 폴더에 풀어 같은 방법으로 잰 실제 값**입니다.
    - 단어 중간 줄바꿈: 15개 화면 상태 × 폭 320 · 360 · 375 · 412 · 480px에서 **59건 → 0건**
    - 칩 · 배지 · 알약 · 버튼의 높이와 글자 줄 수: 폭 280 · 320 · 375px에서 159개를 비교해 **차이 0** (고치기 전과 같음). 칩 44px · 버튼 48px는 320 · 375px에서 한 줄이고, **280px에서는 칩 일부와 배지 일부가 두 줄로 접히는데 고치기 전부터 같았습니다.**
    - 띄어쓰기 없는 긴 글자(한글 55자 · 영문 52자 · 숫자 40자)를 넣어도 320px에서 넘치지 않음: 고치기 전 **40건 → 0건** (영문 20 · 숫자 20, 한글은 원래 0건). 이 40건은 규칙을 무력화해 흉내 낸 값과 측정 60건이 모두 같음을 확인했습니다.
    - (비교 항목) 같은 코드에서 `overflow-wrap: break-word`만 적용하면 flex 안의 칸에서 45건이 넘쳐서 `anywhere`를 함께 씁니다.
- **확인 방식의 한계:**
  - 클릭은 코드로 실행했고, 마우스·터치를 직접 입력한 것은 아닙니다.
  - 시간 흐름은 데모 시계를 앞당겨 확인했습니다. 실제로 10분을 기다린 것이 아닙니다.
  - 화면을 열어 둔 동안 배지를 다시 판단하는 타이머(원래 60초)는 점검에서 **1초로 줄여** 돌렸습니다. 그래서 점검 기록의 "타이머 6번(6초)"은 실제 앱에서는 약 6분에 해당합니다. 시계를 앞당긴 것과 함께 "시간이 흐른 상황"을 빠르게 재현하는 방법이며, 실제 시간이 흐르는 동안의 동작을 지켜본 것은 아닙니다.
  - 외부 글꼴(Pretendard)은 차단된 채로, 시스템 글꼴로 확인했습니다. 그래서 줄바꿈 점검의 "단어 중간에서 끊기지 않음"은 글꼴과 상관없이 의미가 있지만, 두 화면(`stale` 확인 줄, `fail` 안내 상자) 외의 화면은 실제 글꼴에서 줄이 어디서 바뀌는지를 사용자가 직접 확인해야 합니다.
  - 확인이 실패하는 상황은 주소의 `?scenario=` 값을 바꿔 만들었습니다.

## 나중에 할 일

- **이동 시간에 "오래됨" 기준 두기 (미착수, 정하지 않음):** 지금 "오래됨" · 자동 재확인은 항공편 응답만 봅니다. 이동 시간에도 기준을 두려면 먼저 DesignGuide §7에 문구와 기준을 정해야 하고, 후보와 영향 범위는 다음과 같습니다. 기준값 후보: 항공편과 같은 `STALE_AFTER_MIN`(10분)을 재사용하거나 이동 시간 전용 값을 새로 두는 안(교통 상황이 바뀌는 속도는 확인 못 함). 영향 파일: `config.js`(상수), `domain/status.js`(판단), `domain/travelChecked.js`(문구), `ui/screens/result.js`(자동 재확인 · 배지 우선순위 `BADGE_PRIORITY`), `recommendCard.js`, 관련 테스트(`tests/travelChecked.test.js`, `autoRecheck.test.js`, `flightView.test.js`). 이동 시간 시각은 기기 시계이고 항공편 시각은 서버 시계이므로 서로 비교하지 않는 원칙을 유지해야 합니다.
- **숨겨진 탭에서 자동 재확인 멈추기 (미착수, 가정):** 탭이 숨겨진 동안 자동 재확인을 멈추고 다시 보일 때 오래됐으면 한 번만 확인한다. **조건: 배포 후 함수 로그에 `[flights] quota (…)`처럼 한도 초과 사유가 관찰되면 이 항목부터 한다.** (한도 초과 응답을 실제로 받은 적은 아직 없고, 로그 형식은 `server/icn/handleFlights.js` 기준이다.)
- **"다시 시도" 10초 쿨다운 (미착수, 가정):** 연타로 호출이 늘지 않게 한다. 위 항목 다음 순서이고, 문구와 포커스 처리를 DesignGuide에 먼저 정한 뒤 만든다.

## 실제 API로 바꿀 때

1. 항공편 어댑터는 서버 경유 호출로 바꿨습니다(반환 형태는 `{ ok, data }` / `{ ok: false, reason }`, reason은 `notfound` · `missing` · `quota` · `timeout` · `error`). 주소 어댑터(`placeAdapter.js`)도 `POST /api/places` 호출로 바꿨습니다(reason은 `quota` · `timeout` · `aborted` · `error`). 이동 시간 어댑터(`routeAdapter.js`)도 `POST /api/route` 호출로 바꿨습니다(reason은 `noroute` · `quota` · `timeout` · `noterminal` · `error`, 결과 `source`는 `'kakao'`). 그래서 "이동 시간도 다시 확인했어요"가 실제 모드에서도 나오도록 했습니다(브라우저에서 이 문구가 나타나는 것은 아직 확인하지 않음).
2. 시계는 `public/js/clock.js`에서 모드별로 이미 나눴습니다. (실제 모드 = 실제 시각)
3. 주소·이동 시간이 실제로 확인되어 `config.js`의 `ADDRESS_ROUTE_IS_MOCK`을 `false`로 바꿨습니다(상단 표시 없음). 시나리오 모드가 더 필요 없으면 `public/js/mock/`을 제거합니다.
4. 시간·시각은 항상 `Asia/Seoul` 기준으로 `public/js/domain/time.js`의 함수를 거쳐 다룹니다.
